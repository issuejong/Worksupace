# UMC-Night 구현 계획

작성일: 2026-10-13 · 수정일: 2026-10-20 · 시간대: Asia/Seoul

이 문서는 합의된 요구사항과 원래의 커밋 단위 계획을 기록한다. 현재 운영에서는 문제별 배점을 사용하지 않고 인정된 정답 1개씩 누적한다. 아래 과거 구현 단계의 배점 언급은 당시 계획이며, 구현 상태와 실제 배포 절차는 `README.md`를 따른다.

## 1. 확정된 요구사항

- 행사: 동국대학교 동아리 MT `UMC-Night`, 2026-10-30 20:00 시작.
- 완성 목표: 2026-10-23. 레크레이션 종료 시각은 미정이며 검증 시 90분 연속 사용을 기본 시나리오로 가정한다.
- 참가 규모: 팀 수 제한 없이 팀 대표 1명이 휴대폰으로 답안을 제출한다. 예상 인원은 팀당 5~6명이다.
- 진행자는 노트북, 관객은 노트북 확장 화면에 연결된 대형 화면을 사용한다. 현장 와이파이가 있다.
- 게임은 문제 제시부터 답안 제출·채점·결과 발표까지 사이트 안에서 진행한다.
- 진행자가 문제와 비공개 정답을 미리 등록하고, 팀별 답안을 저장한다.
- 팀별 정답 개수를 게임 전체에 걸쳐 누적한다. 인정된 정답은 1개, 오답·미제출은 0개다. 선착순 문제는 첫 정답 팀만 1개를 얻는다.
- 게임과 문제는 나중에 정할 수 있어야 하므로 준비 화면에서 내용·정답 방식·시간·순서를 편집한다.
- 호스팅·데이터 저장 등 서비스 운영 비용은 무료 플랜 범위 내 0원. 무료 외부 서비스 사용 가능.
- 모든 프로젝트 코드·설정·문서는 저장소 루트의 `umc-night/` 내부에 둔다.

## 2. 첫 버전 범위

### 필수

1. 운영자 로그인, 현장 QR 참가, 이름 입력 시 팀 자동 생성과 대표 기기 세션.
2. 문제 준비: 객관식, OX, 주관식. 이미지가 포함된 문제와 정답 공개 이미지 지원.
3. 대기실, 현재 문제, 타이머, 팀별 제출 여부, 공개된 결과, 누적 순위.
4. 진행자 제어: 시작, 일시정지·재개, 답변 마감, 정답 공개, 채점 확정, 다음 문제, 문제 무효 처리.
5. 객관식·OX 자동 판정. 주관식은 등록된 팀의 답안을 나란히 보고 정답·오답으로 판정.
6. 점수 반영 중복 방지, 판정 정정, 변경 이력과 직전 변경 되돌리기.
7. 새로고침·재접속 복구, 저장 성공/실패 안내, 연결 상태 표시.
8. 점수 없는 연습 문제, 별도 리허설 실행, 결과 내보내기와 리허설 초기화.
9. 관리자·팀·관객 권한 분리와 공개 전 정답 보호.

### 핵심 흐름 검증 후 추가

- 참가 QR, 정답 발표 효과, 순위 공개·숨김, 우승팀 등장 연출.
- 효과음과 음소거. 소리는 진행자 노트북 한 곳에서 재생한다.
- 기억력 퀴즈: 제시 화면을 일정 시간 보여준 후 숨기고 질문한다.

### 이번 범위에서 제외

- 부분 점수, 오프라인 게임, 임의 점수를 주는 오프라인 게임 입력 화면.
- 개인별 계정·점수, AI API, 선착순 버저, 점수 베팅, 여러 행사 동시 운영.
- 완전한 오프라인 플레이와 이후 자동 병합.

초성 퀴즈는 주관식 콘텐츠로 구현한다. 이미지 퀴즈도 공통 문제·제출·채점 기능을 사용한다. 게임별로 별도의 점수 체계를 만들지 않는다.

## 3. 디자인과 자산

- 콘셉트: 동국의 밤에 열리는 팀 대항 퀴즈쇼.
- 직접 만든 오렌지 중심 화면, 짙은 차콜 배경, 밝은 크림색 문제 영역.
- 아코는 학교가 배포한 원본 이미지로 사용한다. 원본의 형태와 비율을 유지하며 대기·제출 완료·결과 화면에 배치한다.
- 학교 로고와 동국체는 사용 범위를 확인한 뒤 별도 판단한다. 초기 구현은 시스템 고딕체를 사용하고, 웹 사용이 허용된 글꼴을 확인하면 적용한다.
- 사이트에 `동국대학교 UMC 동아리 행사 진행용 사이트`라는 운영 주체·용도를 표시한다.
- 학교 홈페이지 화면·사진을 그대로 복제하지 않고 화면 구성과 장식을 직접 설계한다.
- 팀 구분은 이름·번호·보조 색을 함께 사용한다. 정답·오답도 글자와 아이콘으로 구분한다.
- 대형 화면은 16:9를 기준으로 문제 가독성을 우선하고, 실제 프로젝터에서 검증한다.
- 모바일은 큰 답안 입력 영역과 제출 버튼, 고정된 팀 이름, 분명한 저장 상태를 제공한다.
- 공개 저장소에는 아코 등 제3자 자산의 이용 조건이 적용됨을 표시하고, 프로젝트 코드 라이선스와 구분해 출처·원문 안내를 기록한다.

## 4. 화면과 경로 제안

| 경로 | 용도 | 핵심 정보와 조작 |
|---|---|---|
| `/` | 참가 안내 | 행사명, 팀 참가, 진행자 진입 |
| `/join` | 팀 대표 참가 | QR 접속, 팀 이름 입력, 자동 등록과 참가 세션 발급 |
| `/play` | 대표 휴대폰 | 현재 문제, 답 입력·수정, 제출 상태, 공개 결과 |
| `/screen` | 대형 화면 | 대기실·문제·타이머·제출 여부·결과·순위 자동 전환 |
| `/admin/setup` | 준비 | 팀·문제·정답 방식·시간·순서·이미지 편집 |
| `/admin/live` | 행사 운영 | 진행 제어, 등록된 팀 답안, 판정, 점수 이력 |

정답 등 운영 정보는 관리 화면에서만 조회한다. 대형 화면과 팀 화면에 제공하는 데이터도 서버에서 각각 제한한다.

## 5. 게임 상태와 점수 규칙

- 기본 흐름: 대기 → 답변 진행 → 답변 마감 → 정답 공개 → 채점 확정 → 결과/순위 → 다음 문제.
- 일시정지 시 남은 시간을 저장하고 답안 접수를 중단한다. 재개하면 새로운 마감 시각을 계산한다.
- 문제별 배점은 없다. 인정된 정답 1개씩 누적하며 미시작 문제는 시간·순서를 바꿀 수 있다.
- 시작한 문제의 내용·정답 방식은 해당 실행에 고정한다. 문제 오류가 있으면 무효 처리하고 모든 팀에 동일하게 적용한다.
- 마감 전까지 답안을 수정할 수 있다. 팀별로 마지막 저장이 성공한 답안 1개가 최종 답안이다.
- 마감 여부는 서버/DB 시간을 기준으로 확인한다. 휴대폰 시각이나 화면의 버튼 상태만으로 접수를 판단하지 않는다.
- 같은 답안 전송을 재시도해도 중복 저장 효과가 생기지 않게 요청 식별자를 사용한다. 오래된 응답이 최신 답안을 덮어쓰지 않도록 버전을 검사한다.
- 객관식·OX는 서버에서 정답 판정. 주관식은 진행자가 정답/오답만 선택한다. 오타·동의어도 동일 기준으로 전부 인정 또는 불인정한다.
- 정답 공개 후 답변을 다시 받지 않는다. 다시 출제해야 하면 새로운 문제 실행을 만든다.
- 판정 확정과 점수 반영은 하나의 원자적 작업으로 처리한다. 확정 버튼 중복 클릭·네트워크 재시도로 점수가 두 번 더해지지 않아야 한다.
- 점수 정정은 기존 판정의 취소와 새 판정을 연결해 기록한다. 임의의 부분 점수 입력은 제공하지 않는다.
- 동점은 공동 순위로 표시한다. 최종 우승팀을 가려야 하면 준비된 결승 문제를 추가 진행한다.
- 순위 비공개 기능을 추가할 경우 화면에서만 숨기지 않고 참가자 응답에서도 비공개 합계가 노출되지 않게 한다.

## 6. 기술 구성 제안

| 구성 | 선택과 이유 |
|---|---|
| 앱 | Next.js App Router + TypeScript. 화면과 서버 API를 한 프로젝트에서 관리 |
| 스타일 | CSS 또는 Tailwind를 사용한 자체 구성. 행사 브랜드와 큰 화면 가독성을 우선 |
| 호스팅 | Vercel Hobby, 기본 제공 주소 사용, Root Directory를 `umc-night`로 지정 |
| DB | Supabase Free의 PostgreSQL. 문제·답안·진행 상태·점수 기록 영속 저장 |
| 이미지 | Supabase Storage의 비공개 저장소. 관리자 업로드, 문제/정답 공개 단계에 따른 접근 제어 |
| 동기화 | 진행 중 약 1초, 대기 중 약 3~5초 간격의 상태 조회. 실시간 게임 상태 응답은 캐시하지 않음 |
| 검증 도구 | Vitest 계열 단위 테스트와 Playwright 계열 다중 브라우저 시나리오. 구체 버전은 구현 시 호환성 확인 |

팀 대표 3대 + 진행자 + 대형 화면의 약 5개 화면을 가정한다. 90분 동안 모두 1초마다 조회하면 약 27,000회다. 제출·편집·정적 파일 요청 등은 별도이며, 실제 사용량은 리허설에서 확인한다.

타이머는 서버의 기준 시각과 마감 시각을 받아 각 화면에서 계산한다. 상태 조회 지연 때문에 늦게 표시되더라도 제출 API는 서버 마감을 일관되게 적용한다. 활성 상태 조회가 없어도 마감 시각 이후 답안은 접수하지 않는다.

무료 서비스 사용은 제공 한도와 계정의 기존 사용량을 전제로 한다. Vercel Hobby의 비상업적 개인 용도 조건, 저장소 연결 조건, Supabase 무료 프로젝트 여유를 배포 전에 확인한다. 유료 플랜·API·도메인은 기본 구성에 포함하지 않는다.

## 7. 데이터와 권한

주요 데이터는 다음과 같이 나눈다.

- 행사 설정과 팀: 행사 이름, 팀 이름, 표시 순서, 대표 기기 세션.
- 문제 원본: 유형, 내용, 보기, 이미지, 제한 시간, 배점, 출제 순서.
- 정답 정보: 정답과 정답 공개 이미지. 공개 문제 데이터와 분리.
- 행사 실행: 리허설/본행사 구분, 현재 문제, 진행 단계, 마감 시각, 상태 버전.
- 문제 실행: 시작 당시 문제·정답·배점의 스냅샷.
- 팀 답안: 실행·문제·팀 조합당 최종 답안 1개, 서버 수신 시각, 버전.
- 판정과 점수 기록: 정답 여부, 부여 점수, 판정자, 변경 사유, 취소 연결 정보.
- 참가 세션: 팀 연결, 토큰 해시, 만료 시각, 폐기 여부.

보안 경계:

1. 운영자 인증은 Supabase Auth의 사전 생성된 운영자 계정을 사용하고, 서버에서 행사 운영 권한을 확인한다.
2. 팀 대표는 현장 QR로 접속해 팀 이름을 입력한다. 중복 이름은 거부하고 등록 시도 횟수를 제한한다.
3. 참가 세션은 추측하기 어려운 토큰을 HttpOnly·Secure 쿠키에 보관한다. 팀은 요청 본문의 팀 번호가 아니라 검증된 세션으로 결정한다.
4. 대표 기기 교체는 진행자가 기존 세션을 폐기한 뒤 재참가시키는 방식으로 처리한다. 두 기기가 같은 팀 답안을 경쟁해서 바꾸지 않게 한다.
5. 브라우저의 DB 직접 접근은 기본 차단하고 서버 API를 통한다. 서버 전용 키는 환경 변수로 관리한다. 상태 변경 요청의 출처와 권한을 검증한다.
6. DB 접근 정책도 기본 거부로 설정하고, 공개 전 정답·타 팀 답안·관리 정보를 참가자에게 반환하지 않는다.
7. 답안 제출·마감·채점은 DB 트랜잭션과 제약조건으로 경쟁 상태를 처리한다. 서버 인스턴스 메모리에만 상태를 저장하지 않는다.
8. 이미지 파일명으로 정답을 추측할 수 없게 저장하고, 정답 이미지 주소는 공개 시점 이후에만 제공한다. 업로드 형식과 크기를 제한한다.

## 8. 당초 커밋 단위 구현 계획

아래는 구현 전 구상한 커밋 14개의 순서다. 실제 구현에서는 검증 가능한 기능 단위로 묶어 커밋하며, 현재 상태는 Git 기록과 `README.md`를 기준으로 확인한다. 경로는 모두 `umc-night/` 기준의 예정 위치이며 구현에 맞춰 세부 파일명은 조정할 수 있다.

### 커밋 원칙

- 한 커밋은 한 가지 목적을 갖는다. UI·API·DB 변경이 하나의 기능을 완성하는 데 필요하면 같은 커밋으로 묶는다.
- 각 커밋에서 빌드와 타입 검사를 통과하고, 해당 기능에 필요한 테스트를 함께 실행한다. 마지막에 테스트를 몰아넣지 않는다.
- 점수, 권한, 제출·마감 경쟁 상태는 실제 DB 제약조건과 트랜잭션을 검증한다. API를 전부 모의 처리한 테스트만으로 통과시키지 않는다.
- UI만 바뀌는 커밋은 모바일·대형 화면에서 시각적으로 검증한다. 스타일 값을 그대로 비교하는 테스트는 만들지 않는다.
- 미완성 기능은 작동하는 것처럼 표시하지 않는다. 디자인용 샘플 데이터와 정답은 개발 전용 프리뷰에 한정한다.
- DB 마이그레이션은 추가 방식으로 관리한다. 기존 행사 데이터를 유지하면서 앞으로 적용할 수 있어야 하며, 앱 커밋 되돌리기가 DB를 자동 복구한다고 가정하지 않는다.
- 비밀키·실제 행사 정답 데이터·환경 변수 파일은 Git에 넣지 않는다. `.env.example`에는 변수명과 예시만 기록한다.
- 각 번호는 목표 단위다. 검증 중 발견한 독립적인 오류는 별도 `fix` 커밋으로 남길 수 있다.

- Vercel Root Directory, 환경 변수, DB 마이그레이션, 운영자 계정 설정, 무료 한도·서비스 활성 확인, 예비 핫스팟 복구 절차를 문서화한다.
- 선행 조건: 12~13. 배포 계정 연결과 실제 기기 점검 환경.
- 완료 기준: 빌드·타입 검사·기능 테스트 통과, 실제 다섯 화면 완주, 90분 사용과 재접속 검증. 자동 검증과 사람이 실제 기기에서 확인한 항목을 구분해 기록한다.

**배포는 검증된 커밋을 대상으로 수행한다.** Vercel·Supabase의 계정 연결과 환경 변수 입력은 외부 설정 작업이며 비밀값을 커밋하지 않는다. 프리뷰와 본행사는 데이터를 분리하고, 프리뷰 코드가 본행사 데이터를 초기화하지 못하게 한다. 환경 연결이 확보되지 않으면 로컬에서 검증 가능한 작업을 먼저 완료하고 배포·다중 기기 검증은 미완료로 명시한다.

### 후속 후보

- 기억력 퀴즈, 효과음·음소거는 필수 범위와 리허설 통과 후 각각 별도 기능 커밋으로 검토한다.
- 기능을 추가하다 일정이 부족하면 필수 기능 검증을 우선한다.

## 10. 검증과 운영

- 실제 휴대폰 3대와 진행자 노트북 두 화면으로 참가부터 최종 순위까지 진행한다.
- 문제별 여러 팀 동시 제출, 마감 경계에서의 제출, 일시정지 중 제출을 검증한다.
- 반복 제출·응답 역전·채점 중복 클릭·두 탭의 관리자 조작에도 중복 점수가 생기지 않아야 한다.
- 제출 직후 새로고침해도 저장된 답안과 접수 상태가 복구되어야 한다. 서버 확인 전에 제출 완료로 표시하지 않는다.
- 연결이 끊기면 연결 상태를 명확히 표시하고, 복구 후 최신 상태를 다시 읽는다. 마감 후의 오프라인 답안을 자동 접수하지 않는다.
- 개발자 도구로 응답을 확인해도 공개 전 정답·타 팀 답안·관리자 정보가 노출되지 않아야 한다.
- 재채점·취소 전후에 화면의 총점과 점수 이력의 합계가 일치해야 한다.
- 리허설 초기화는 리허설 답안·판정·진행만 초기화하고 문제·팀·본행사 결과를 보존한다.
- 이미지 업로드·조회 권한과 정답 이미지 공개 시점을 확인한다.
- 90분 연속 사용을 기준으로 화면 절전 복귀·브라우저 재접속·API 사용량을 점검한다.
- Supabase 무료 프로젝트의 비활성 일시정지 여부를 행사 전날과 당일 확인한다.
- 인터넷 장애 때는 진행을 일시정지하고 예비 핫스팟으로 복구한다. 모든 게임이 웹에서 진행되는 만큼 안정적인 예비 연결이 중요하다.
- 운영자만 전체 문제·정답·결과를 내보낼 수 있게 한다. 행사 전 콘텐츠와 행사 후 결과를 보관한다.

## 11. Codex 모델 추천

- 주력 구현: `GPT-6.1 Sol`. 이 프로젝트에서는 여러 화면·DB·권한·채점 흐름을 함께 다루므로 reasoning `High`를 제안한다. 이는 프로젝트 특성에 따른 제안이며, 공식 문서는 기본 effort에서 시작해 필요에 따라 올리도록 안내한다.
- 가장 까다로운 설계·오류 분석·최종 검토: `GPT-6 Astra`. 기본 effort부터 시작하고 복잡한 동시성 문제에 필요하면 높인다.
- 범위가 좁고 기준이 명확한 문구·간격 수정: Sol의 낮은 effort 또는 `GPT-6 Luna`.
- 모델을 자주 바꾸기보다 한 채팅에서 이 계획과 단계별 완료 기준을 유지한다. 실제 선택 가능 모델은 계정과 클라이언트에 따라 다르다.
- 사이트 자체에는 AI 모델 API를 사용하지 않는다. Codex 개발 이용량은 사이트 호스팅·DB 운영 비용과 별개다.
