# Young Planner AI 고도화 구현 계획

작성일: 2026-11-05 · 기준 커밋: `62fe893`

> 최신 입력 UX와 작업 순서는 [대화·직접 입력 통합 계획](dual-input-implementation-plan.md)을 우선한다. 두 방법은 공통 입력 상태를 사용하고, 권 부장 부부 값은 예시 버튼으로만 채운다. 이 문서의 7단계였던 대화 기반 입력은 새 계획에 따라 선행 구현하며, 아래 분석 기능 설계는 이후에 이어서 적용한다.

목표는 사용자의 질문과 선호를 이해하고, 검증된 계산 결과로 은퇴 계획을 비교하며, 조건을 바꿔도 대화를 이어가는 챗봇이다. 이 문서는 구현 계획이며 앱 코드를 변경하지 않는다.

## 1. 현재 상태와 범위

현재 실행 코드의 도구는 `inspect`, `compare`, `search` 세 가지다. `docs/agent-v1.md`는 이전 버전 기록이므로 현재 기능 명세로 사용하지 않는다.

- `src/lib/household-agent.ts`: 도구 정의·계산 호출·모델 호출 반복·자연어 답변 반환.
- `src/app/api/agent/route.ts`: 요청 검증·접근 토큰·호출 제한·제공자 연결·시간 제한.
- `src/app/planner.tsx`: 가구/계획 상태·대화·후보 적용/되돌리기·플로팅 챗봇.
- `tests/household-agent.test.ts`: 계산 도구와 모의 모델 중심의 테스트. 실제 모델 평가와 구분한다.

점검에서 확인한 보완점:

1. 도구를 실행했는지는 검사하지만 최종 설명이 계산 결과와 일치하는지는 검사하지 않는다. 모의 모델이 자산 소진 여부를 반대로 설명해도 통과했다.
2. 모든 질문의 첫 호출에 도구 실행을 강제한다. ‘국민연금은 최대 몇 개월 미룰 수 있어?’가 정규식 때문에 조합 탐색 질문으로 처리되는 오류 경로를 재현했다.
3. 현재 조건과 같은 snapshot의 대화만 전송하므로 조건 변경·후보 적용 뒤 이전 상담 맥락이 전달되지 않는다.
4. 탐색에 자산 소진 금지는 있지만 비상자금 유지 제약은 없다. 두 조건은 별개다.
5. 생활비 한도·스트레스 테스트 전용 도구, 자료 검색, 대화로 입력안을 만드는 기능이 없다.

## 2. 유지할 기준

- `finance.ts`, `household.ts`의 검증된 월별 산식과 보고서 기준 수치는 유지한다.
- 현재 Gemini/OpenAI 연결과 환경변수 방식을 유지한다. 모델 교체·자체 학습·유료 제공자 자동 전환은 범위에 넣지 않는다.
- 플로팅 로봇 버튼, 채팅창 위치, Enter/Shift+Enter, 후보 적용·되돌리기를 유지한다.
- AI가 설명과 대화를 담당한다. 실패 시 기존에 제거한 정형 계산 설명으로 대체하지 않는다.
- 계산·비교는 설정을 변경하지 않는다. 입력안과 추천안은 사용자가 확인하고 적용해야 반영한다.
- 로그인·서버 DB·입력값 자동 저장을 추가하지 않는다. 상담 맥락은 현재 브라우저 세션의 메모리에서 유지한다.
- 화면 소수점 한 자리 표시와 내부 계산 정밀도 보존을 유지한다.
- 금융자산·순자산, 명목금액·기준년 구매력, 비상자금 미달·자산 소진을 구분한다.

## 3. 목표 흐름

질문과 현재 조건 → 의도·대상·목표 확인 → 필요한 경우 확인 질문 → 계산/자료 조회 → 근거 묶음 생성 → AI 답변 생성 → 근거 검증 → 설명·비교 카드 표시 → 사용자 적용.

모든 질문을 길게 분류·계산하지 않는다. 인사나 사용법은 간단히 답하고, 수치 비교에는 계산 도구, 제도 설명에는 승인된 자료를 사용한다. 실제 호출 횟수와 시간은 공통 예산 안에서 관리한다.

새 모듈은 `src/lib/assistant/`에 역할별로 나누고, 기존 `household-agent.ts`를 단계적으로 연결 지점으로 정리한다. 엔드포인트는 `/api/agent`를 유지한다.

## 4. 단계별 구현과 완료 기준

### 0단계 — 평가 기준과 회귀 질문 준비

`tests/ai/fixtures/`와 별도 평가 스크립트를 만든다. 자동 테스트와 실제 모델 평가를 분리한다.

- 대표 질문 40개: 결과/원인 8, 비교 6, 목표·고정 조건 6, 맥락을 잇는 대화 8, 지식/확인 질문 6, 입력·오류·범위 밖 질문 6.
- 각 사례에 기대 의도, 필요한 도구, 변경해도 되는 조건, 유지해야 할 조건, 금지 주장, 계산 기준값을 기록한다.
- 단위·통합 테스트는 모의 모델로 실행하고, 실제 모델 평가는 명시적인 명령으로만 실행한다. 기본 `npm test`에 외부 API 호출을 넣지 않는다.
- 비교 대상: 의도·도구·인자 정확성, 계산값 일치, 제약 준수, 근거 없는 단정, 후속 질문 처리, 응답 시간, 도구/모델 호출 수, 실패율.
- 실제 사용자 재무정보나 대화를 자동 수집하지 않고 예시·팀 검토 질문을 사용한다.

완료 기준: 같은 평가 입력으로 변경 전후 결과를 비교할 수 있고, 점검에서 발견한 문제를 평가 항목으로 재현한다. 알려진 실패를 숨기거나 기준 답을 현재 오류에 맞춰 바꾸지 않는다.

### 1단계 — 계산 근거와 답변 검증

추가 파일: `assistant/evidence.ts`, `assistant/answer.ts`, `assistant/validate-answer.ts`.

- 계산마다 `runId`, `scenarioId`, 조건 버전, 기준 연도, 단위가 붙은 근거 목록을 만든다.
- 지표뿐 아니라 특정 월의 전월 잔액·수입·지출·월말 잔액·구성 항목·소득 시작/종료 이벤트를 제공한다.
- AI는 검증 가능한 답변 구조를 반환한다. 수치·날짜·비교는 근거 ID를 참조하고, 화면에는 해당 계산값을 연결한다.
- 존재하지 않는 근거, 다른 시나리오의 숫자, 명목/실질 혼동, 자산 소진/비상자금 상태 모순을 검출한다.
- ‘왜 부족한가’는 해당 월의 흐름과 이전 잔액에 근거한다. 여러 조건이 바뀐 효과를 단일 요인의 기여로 단정하지 않는다.
- 실패하면 검증 피드백을 넣어 한 번 재생성한다. 그래도 실패하면 설명을 완료하지 못했음을 알리고 재시도를 제공한다. 재생성도 전체 호출 예산에 포함한다.
- 구조화 출력만으로 자유로운 설명의 의미적 정확성이 보장되지는 않으므로 문장·원인 설명은 별도 평가와 팀 검토를 유지한다.

완료 기준:

- 도구가 ‘소진 없음’인데 AI가 소진을 주장하는 모의 응답을 차단한다.
- 잘못된 날짜·금액·기준 연도·후보 참조를 차단한다.
- 보고서 예시와 엔진 회귀 수치가 그대로 일치한다.

### 2단계 — 질문 분류와 확인 질문

추가 파일: `assistant/intent.ts`, `assistant/clarification.ts`.

- 처리 유형: 결과 조회, 원인 분석, 변경 비교, 목표 탐색, 생활비 한도, 위기 분석, 자료 설명, 입력안 작성, 확인 질문, 사용법/일반 대화.
- ‘최대’, ‘최적’ 정규식으로 도구를 강제하는 방식을 제거하고 질문의 목적과 계산 대상을 구분한다.
- 인사·사용법·확인 질문에는 계산 도구를 강제하지 않는다. 수치 답변에는 근거가 필요하다.
- ‘가장 좋은 안’처럼 목적이 모호하면 기말 금융자산·기간 중 최저 자산·비상자금 유지 중 무엇을 원하는지 선택하게 한다.
- 누락된 정보는 필요한 것만 묻고, 분명한 질문은 바로 처리한다. 설명과 비교가 섞인 질문도 함께 처리한다.

완료 기준: ‘연금은 최대 몇 개월 미뤄?’를 자산 탐색으로 오인하지 않으며, ‘최저 잔고가 가장 높은 안’과 ‘마지막 자산이 가장 많은 안’의 목표가 구분된다.

### 3단계 — 상담 맥락과 시나리오 버전

추가 파일: `assistant/context.ts`, 프런트의 대화 상태를 별도 훅으로 분리.

- 기억할 내용: 상담 목표, 사용자가 명시한 고정 조건, 현재 시나리오, 원래 비교안, 최근 후보 ID, 마지막 적용/되돌리기.
- 조건 변경을 이유로 대화를 버리지 않는다. 과거 숫자를 현재 계산으로 사용하지 않도록 조건 버전과 후보 입력을 구분하고 필요한 값은 재계산한다.
- ‘그 안’, ‘두 번째 안’, ‘방금 적용하기 전’의 대상을 명시적인 ID로 찾는다.
- 서버는 전달받은 과거 수치를 신뢰하지 않고 가구·계획 입력을 검증한 뒤 다시 계산한다.
- 과거 후보 적용 전 현재 조건과 분석 조건을 확인한다. 다르면 ‘현재 조건으로 다시 비교’를 제공한다.
- 새 상담 시작 동작은 대화와 상담 목표를 정리하고, 예시 넣기·조건 불러오기와 구분한다.

완료 기준: 후보 적용 → 생활비 수정 → ‘적용 전과 다시 비교해 줘’의 흐름이 이어지며, 예전 수치가 현재 결과로 표시되지 않는다. 자동 저장은 추가되지 않는다.

### 4단계 — 목표·제약·실행 가능성을 반영한 탐색

추가 파일: `assistant/search.ts`, `assistant/constraints.ts`.

- 목표, 고정 조건, 선택 가능한 준비 방법, 실제 자격 확인 상태를 구분한다. 모델이 현재 값을 모두 고정해 탐색을 끝내지 않도록 사용자 의도와 대조한다.
- `requireNoShortfall`과 `requireReserve`를 별개 제약으로 지원한다.
- ‘재취업하지 않겠다’는 명시 조건을 고정하고, 생활비·수익률을 임의로 바꾸지 않는다.
- ‘집을 남기고 싶다’는 선호만으로 주택연금을 자동 제외하지 않는다. 제외를 원하는지 확인한다.
- 개인 입력에서 구직급여·추납·주택연금 자격이 불명확하면 확인 질문 또는 조건부 비교로 표시한다. 보고서 예시는 보고서의 가정으로 구분한다.
- 현재 일부 시점만 비교하는 탐색 범위를 명시적인 설정으로 만든다. 후보 범위를 넓히되 서버의 최대 계산 횟수·시간 예산을 적용한다.
- 완료 여부, 비교한 조합 수, 범위, 제약을 만족한 후보 수를 반환한다. 범위 내 최상위와 전역 최적을 구분한다. 시간 초과·중단 결과를 전체 탐색 완료라고 표시하지 않는다.
- 경고 문장 정규식 대신 계산 결과의 구조화된 상태 코드를 사용하는 방식으로 옮긴다. 기존 경고 문구와 계산값은 보존한다.

완료 기준: 비상자금 유지 요청에는 `passes=false`인 후보가 최종 추천으로 나오지 않고, 사용자가 고정한 조건이 모두 유지된다. 해가 없으면 제약을 몰래 풀지 않고 완화할 조건을 물어본다.

### 5단계 — 생활비 한도와 위기 상황 도구

추가 도구: `find_spending_limit`, `stress_test`.

- 생활비 한도: 현재의 다른 조건을 고정하고 자산 소진 금지/비상자금 유지 기준별 월 생활비 상한을 찾는다.
- 엔진 입력 범위 안에서 계산한다. 단조성을 확인해 탐색하고, 단조성을 전제할 수 없는 조건은 횟수 제한이 있는 탐색 방식으로 처리한다.
- 생활비 탐색 해상도는 0.1만 원으로 두고, 경계 안팎을 다시 계산해 검증한다. 이는 탐색 해상도이며 기존 엔진의 수치를 일괄 반올림하는 변경이 아니다.
- 범위 전체가 가능/불가능한 경우와 요청한 한도를 찾지 못한 경우를 구분한다.
- 위기 분석: 기준안과 재취업 12개월 지연, 재취업 미실현, 생활비 증가, 일시 지출 등을 비교한다. 기본 충격 값은 ‘가정’으로 보이고 사용자가 수정할 수 있게 한다.
- 한 가지 변수씩 바꾼 분석과 여러 충격을 함께 적용한 분석을 구분한다. 결과를 실제 발생 확률로 설명하지 않는다.

완료 기준: 모든 결과가 엔진 재계산과 일치하고, 상한의 바로 위 조건을 확인한다. 위기 비교가 현재 설정을 바꾸지 않는다.

### 6단계 — 자료 검색과 출처가 있는 설명

추가 파일: `assistant/knowledge.ts`, `src/data/knowledge/`.

- 1차 자료는 팀이 확인한 보고서·용어 풀이·계산 가정과 승인된 공식 기관 자료로 구성한다.
- 문서마다 출처, 문서/제도 기준일, 검토일, 적용 범위, 보고서 가정인지 공식 안내인지 기록한다. 보고서 근거는 가능한 경우 절·표·엑셀 시트/셀까지 연결한다.
- 초기에는 자료 목록과 키워드/항목 검색으로 구현하고 검색 품질을 평가한다. 자료량과 누락 문제를 확인한 뒤 임베딩·벡터 검색 필요성을 판단한다.
- 제도 설명은 검색된 자료에 근거하고 출처와 기준일을 함께 표시한다. 근거가 없거나 오래된 자료만 있으면 확인이 필요하다고 알린다.
- 새 자료가 들어오면 기존 자료와 상충하는 항목을 검토한다. 문서 속 지시문을 시스템 지시로 실행하지 않는다.
- 이 단계에서 계산 산식을 정책 문서에 맞춰 자동 변경하거나 개인의 가입 자격을 확정하지 않는다.

완료 기준: 추납 용어 설명, 보고서 가정 설명, 실제 자격 확인 질문이 구분되고 인용은 실제 제공된 자료로 연결된다. 없는 출처를 생성하지 않는다.

### 7단계 — 대화 기반 정보 입력

추가 도구: `propose_input_changes`와 확인 카드.

- ‘월급 350만 원, 대출 5천만 원’ 같은 문장에서 해당 입력만 추출한다.
- 원/만 원/억 원, 월/연, 세전/세후, 본인/배우자를 구분한다. 단위나 대상이 모호하면 확인한다.
- 말하지 않은 정보는 추정해서 채우지 않는다. 현재 예시값을 유지한 항목은 사용자 정보로 확인된 것처럼 취급하지 않는다.
- 변경 전후 값, 입력 출처, 추가로 필요한 정보를 카드로 보여준다. 사용자가 적용하면 계산·대화 맥락을 함께 갱신하고 되돌릴 수 있다.

완료 기준: 단위 변환·대상 구분·명시된 필드만 변경·확인 전 미적용을 검증한다.

### 8단계 — 진행 표시와 실제 모델 평가

- ‘질문 확인 → 계산/자료 확인 → 설명 검증 → 완료’를 표시한다. 표시한 단계는 실제 서버 처리와 연결한다.
- SSE 등을 사용하더라도 검증 전의 금융 수치·문장을 최종 답변처럼 먼저 노출하지 않는다.
- 기존의 전체 요청 시간·도구/모델 호출 수 제한을 공통 예산으로 관리한다. 검증 재생성·검색·탐색도 예산에 포함한다.
- 취소, 제한 도달, 연결 실패, 설명 검증 실패, 후보 적용, 조건 변경 후 재계산 상태를 구분한다.
- 동일 계산의 요청 내 중복 실행을 줄인다. 개인 입력을 서버 캐시에 장기간 저장하지 않는다.
- 단계별 실제 모델 평가를 누적하고 최종 40개 질문을 반복 실행해 일관성·호출 수·응답 시간·오류를 비교한다.
- 규칙으로 판정 가능한 수치/조건은 코드로 채점하고, 자연어 원인 설명·도움 정도는 팀이 함께 검토한다. 단순 ‘응답 성공’만 품질 통과로 보지 않는다.

완료 기준: 아래 최종 기준을 충족하며 실제 모델 평가와 모의 테스트 결과를 구분해서 기록한다.

## 5. 커밋 단위

각 커밋은 관련 테스트와 문서 변경을 포함한다. 처음 평가 세트는 변경 전 실패 항목을 드러내는 기준 보고서로 사용하고, 단계별 수정 후 회귀 통과 기준으로 전환한다.

| 순서 | 예정 커밋 | 주요 내용 |
|---|---|---|
| 1 | `feat(AFPK): AI 평가 질문과 기준 결과 기록 추가` | 대표 질문·기대 도구·기준값·평가 스크립트 |
| 2 | `fix(AFPK): 계산 근거와 AI 설명 일치 검증 추가` | 근거 ID·답변 구조·모순 검증·재생성 |
| 3 | `fix(AFPK): 질문 의도와 확인 질문 처리 개선` | 불필요한 계산 강제·최대 정규식 오인 해결 |
| 4 | `feat(AFPK): 시나리오 버전과 상담 맥락 유지` | 목표·고정 조건·이전 후보·후속 비교 |
| 5 | `feat(AFPK): 목표와 제약을 반영한 은퇴 계획 탐색` | 비상자금 제약·실행 가능성·탐색 범위 |
| 6 | `feat(AFPK): 생활비 한도 계산 도구 추가` | 유계 탐색·상한 검증·해 없음 처리 |
| 7 | `feat(AFPK): 은퇴 위기 상황 비교 도구 추가` | 지연·재취업 실패·지출 충격 비교 |
| 8 | `feat(AFPK): 검토 자료 검색과 출처 있는 설명 추가` | 자료 목록·검색·근거/기준일 표시 |
| 9 | `feat(AFPK): 대화 기반 입력안 확인과 적용 추가` | 필드 추출·단위·확인 카드·되돌리기 |
| 10 | `style(AFPK): 챗봇 분석 진행과 상담 결과 표시 개선` | 처리 단계·제약 조건 칩·오류/부분 완료 표시 |
| 11 | `fix(AFPK): 실제 모델 평가와 운영 흐름 검증 보완` | 실제 응답 평가·회귀·브라우저 검증·운영 안내 |

## 6. 최종 검증 기준

반드시 통과시킬 자동 검사:

- 기존 계산 회귀·엑셀 7개 안 × 410개월 = 2,870개월 대조 유지.
- 답변에 연결되는 지표·날짜·단위·시나리오 참조가 계산 근거와 일치.
- 비상자금과 자산 소진을 구분하고 명시된 고정 조건을 위반하는 추천을 차단.
- 확인되지 않은 입력을 자동 적용하지 않고, 과거 후보/숫자를 현재 결과로 사용하지 않음.
- 잘못된 도구 인자·범위 밖 입력·예산 초과·취소·실패 시 현재 설정 보존.
- 비밀값·전체 재무 입력을 오류 기록에 노출하지 않음.
- 타입 검사, 프로덕션 빌드, PC·모바일 챗봇·적용·되돌리기 확인.

실제 모델 평가는 완벽한 의미 검증을 보장하지 않는다. 금융 수치/조건의 명시적인 오류가 발견되면 출시 전에 해결하고, 분류 정확도·대화 도움 정도·응답 시간 등은 변경 전후 실측 결과로 보고한다. 질문 수나 단위 테스트 통과를 실제 AI 정확도로 바꾸어 표현하지 않는다.

대표 브라우저 시나리오:

1. ‘추납이 뭐야?’ → 근거가 있는 용어 설명 → ‘우리 조건에서 비교해 줘’ → 후보 확인.
2. ‘가장 좋은 계획’ → 목표 확인 → ‘비상자금은 유지하고 재취업은 제외’ → 제약을 만족한 안 또는 해 없음.
3. 후보 적용 → 생활비 수정 → ‘적용 전과 비교’ → 버전이 구분된 재계산 → 되돌리기.
4. ‘생활비 얼마까지?’ → 한도 → ‘재취업이 1년 늦으면?’ → 충격 비교.
5. 대화로 가구 정보 입력 → 모호한 단위 확인 → 변경안 적용 → 결과 확인.

## 7. 팀 자료와 출시 순서

자료가 없어도 0~5단계는 현재 보고서 가정으로 진행할 수 있다. 다음 자료가 확정되면 6단계를 채운다.

- 팀 검토를 거친 용어 풀이와 설명 문장.
- 보고서 가정의 근거 위치와 기준일.
- 최신 공식 자료 목록과 자료 갱신 담당자.
- 자격·월액 등을 모를 때 사용자에게 물어볼 항목과 확인 안내.
- 공모전 데모 질문과 팀이 기대하는 답변/비교 조건.

첫 검토 지점은 **1~4단계: 설명 검증·질문 이해·맥락·조건부 추천**이다. 이어서 **5단계: 생활비 한도·위기 분석**, **6~7단계: 자료 설명·대화 입력** 순서로 검토한다. 구현·평가는 로컬에서 진행하고 푸시·배포는 별도 요청 때 실행한다.
